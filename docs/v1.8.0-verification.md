# Tabkha v1.8.0 verification

## Project and compatibility

The Android Studio checkout was fast-forwarded from v1.7.1 to v1.7.9 before this cleanup. Existing uncommitted work was preserved in a named Git stash. Its useful cooking workspace and regression test were integrated into the current code; stale version metadata was not reapplied.

v1.8.0 uses versionCode 36 and retains application ID `com.example.dishroulette`, existing preference keys, recipe IDs, cooking progress keys and the Android Keystore credential format. It supports API24 and later. The abandoned OpenGL device requirement has been removed. The standalone optional backend and provisioning/private-build tools remain development tools; they are not part of the Android runtime.

Removed the Advanced renderer, gesture/inspection classes, mechanical audio implementation and samples, hidden controls, duplicate tablet layout, no-op adapter contract, unused dependency, obsolete icons/text/styles/colors, pre-API24 launcher raster fallbacks and template/retired Advanced tests. Lint reports no unused resources after cleanup.

## Build and local logic checks

```sh
./gradlew assembleDebug assembleDebugAndroidTest assembleRelease lintDebug \
  :app:testDebugUnitTest :recipe-core:test :backend:test --offline --console=plain
```

Debug and optimized release builds pass. JVM tests: **72 passed** (app 37, recipe-core 17, backend 18).

Lint: **0 errors, 0 unused resources**. The 14 remaining advisory warnings concern dependency/catalog maintenance and two views intentionally constructed programmatically with activity/controller arguments. They are not runtime test failures. Dependency versions were retained to avoid combining this cleanup with an unrelated dependency migration.

The normal debug APK and unsigned optimized release APK were inspected as ZIP archives: neither contains the private bootstrap asset nor the locally configured owner key. The installable debug artifact retains the existing local debug signing identity. The unsigned release artifact is a build validation output, not the uploaded installable asset.

## Emulator checks

Device: Pixel_7 emulator, Android API34. Tests use an isolated emulator because fixtures modify preferences, recipes and credential setup. Ordinary tests make no provider requests; live checks are explicit.

The native suite covers generation success/cancellation/retry, late callbacks, rotation and editing identity, English/Arabic RTL, meal Apply/Cancel semantics, themes, navigation geometry, photo preparation/review, saved recipes, bilingual sharing/import, cooking progress, foreground timers and screen-awake behavior. Navigation checks cover both the icon-above-label layout and the compact row layout used with larger text.

Import UI tests wait for keyboard dismissal before tapping a dialog that changes position. Saved-card fixtures contain both languages so their ordinary open path does not depend on an external translation request.

The full instrumentation run passed: **46 tests**. Additional layout runs passed at the following sizes, in English and Arabic:

| Window | Text size | Checks |
| --- | --- | --- |
| Phone, 1080×2400 / 420 dpi | 100% | Navigation, keyboard, preferences, Home/result/Saved/Settings/cooking |
| Phone, 1080×2400 / 420 dpi | 130% | Full suite, including compact navigation rows |
| Tablet, 1280×1920 / 160 dpi | 130% | Centered page widths, responsive flows, preferences and cooking workspace |
| Short landscape, 1920×1080 / 420 dpi | 130% | Scroll reachability, responsive flows and compact preferences |

The emulator was restored to its original display settings and 130% text afterward. Android Studio opened the updated checkout and completed its Gradle sync successfully.

The owner connection was provisioned into the emulator's encrypted store after fixture tests. The live English generation check initially returned `PROVIDER_UNAVAILABLE`; a retry succeeded. The provider model metadata check returned HTTP200. Both English and Arabic live generation checks passed with complete bilingual recipe text. The initial failure was transient provider availability, not a credential rejection.

## Limits

Emulator checks cover representative layouts rather than every physical device. Cooking timers remain visual in-app timers without background alarms. Recipe generation and translation depend on an available configured provider; nutrition remains an estimate. A passing suite is evidence for the tested paths, not a guarantee that no future issue can occur.
